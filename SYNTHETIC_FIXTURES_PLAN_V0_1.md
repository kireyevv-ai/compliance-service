# SYNTHETIC_FIXTURES_PLAN_V0_1.md

## Назначение

Этот план материализует Golden Dataset в небольшой набор synthetic-site сценариев.  
Один fixture должен покрывать несколько правил, чтобы не создавать лишнюю инфраструктуру и десятки почти одинаковых сайтов.

### Принцип

- Golden Dataset остаётся эталоном на уровне Rule.
- Fixture — удобный источник Facts/Evidence.
- Один fixture может намеренно активировать несколько правил.
- Для каждого «плохого» fixture должен существовать либо healthy baseline, либо явный control state.
- Спорные юридические квалификации не имитируются через LLM: fixture задаёт технические факты, Rule Engine определяет ожидаемый статус.

## Набор fixtures

### 1. `healthy-b2b`

- **тип:** B2B
- **сценарий:** Корректная форма, доступная политика, явное согласие, без маркетинговой подписки и сомнительных внешних data flows.
- **основные правила:** `PD-001`, `PD-002`, `PD-003`, `PD-004`, `PD-005`, `PD-006`, `PD-007`, `PD-008`, `PD-009`

### 2. `pd-no-policy`

- **тип:** B2B
- **сценарий:** Форма имя+телефон; политика нигде не найдена.
- **основные правила:** `PD-001`

### 3. `pd-broken-or-restricted-policy`

- **тип:** B2B
- **сценарий:** Два маршрута: битая ссылка на policy и policy за auth.
- **основные правила:** `PD-002`, `PD-004`

### 4. `pd-consent-bad`

- **тип:** B2C_SERVICE
- **сценарий:** Согласие объединено с условиями; checkbox заранее отмечен; маркетинг bundled/prechecked.
- **основные правила:** `PD-005`, `PD-006`, `PD-010`, `PD-011`

### 5. `pd-consent-uncertain`

- **тип:** B2B
- **сценарий:** Форма собирает ПД; checkbox не найден; возможное иное основание неизвестно.
- **основные правила:** `PD-007`

### 6. `pd-consent-text-weak`

- **тип:** B2C_SERVICE
- **сценарий:** Текст согласия без конкретной цели и с формулировкой «любые данные для любых целей».
- **основные правила:** `PD-008`, `PD-009`

### 7. `pd-marketing-uncertain`

- **тип:** B2C_SERVICE
- **сценарий:** Подписка/маркетинговое использование заявлено, но доказательство предварительного согласия извне не видно.
- **основные правила:** `PD-012`

### 8. `pd-policy-incomplete`

- **тип:** B2C_SERVICE
- **сценарий:** Policy без целей, категорий данных, retention/deletion и порядка обращений.
- **основные правила:** `PD-013`, `PD-014`, `PD-015`, `PD-016`

### 9. `pd-policy-reality-mismatch`

- **тип:** B2C_SERVICE
- **сценарий:** Форма собирает поле, которого нет в policy; внешний сервис не указан; policy утверждает, что третьим лицам ничего не передаётся.
- **основные правила:** `PD-017`, `PD-018`, `PD-019`

### 10. `pd-foreign-flow-risk`

- **тип:** B2C_SERVICE
- **сценарий:** На странице формы иностранный endpoint; form action/config указывает иностранный домен; место первичной БД неизвестно.
- **основные правила:** `PD-020`, `PD-021`, `PD-022`

### 11. `pd-rkn-registry-risk`

- **тип:** B2C_SERVICE
- **сценарий:** Оператор надёжно идентифицирован, автоматическая обработка есть, совпадение в реестре РКН не найдено.
- **основные правила:** `PD-023`

### 12. `pd-special-category`

- **тип:** B2C_SERVICE
- **сценарий:** Форма с полем/контекстом, похожим на сведения о здоровье.
- **основные правила:** `PD-024`

### 13. `healthy-ecommerce-legal`

- **тип:** ECOMMERCE
- **сценарий:** Юрлицо: оферта доступна; наименование, ОГРН, адрес, контакты, претензионный порядок; нет preselected add-ons; цены в рублях.
- **основные правила:** `EC-001`, `EC-002`, `EC-003`, `EC-004`, `EC-005`, `EC-006`, `EC-010`, `EC-011`, `EC-012`, `EC-013`

### 14. `ecommerce-legal-missing`

- **тип:** ECOMMERCE
- **сценарий:** Юрлицо: отсутствуют оферта/часть реквизитов/контакты/порядок претензий.
- **основные правила:** `EC-001`, `EC-003`, `EC-004`, `EC-005`, `EC-006`, `EC-010`

### 15. `ecommerce-broken-offer`

- **тип:** ECOMMERCE
- **сценарий:** Ссылка на оферту есть, но возвращает ошибку.
- **основные правила:** `EC-002`

### 16. `ecommerce-ip-missing`

- **тип:** ECOMMERCE
- **сценарий:** Продавец ИП: отсутствуют ФИО, ОГРНИП и контакты.
- **основные правила:** `EC-007`, `EC-008`, `EC-009`

### 17. `ecommerce-paid-addons`

- **тип:** ECOMMERCE
- **сценарий:** Checkout с заранее выбранной платной допуслугой и сценарием обязательной покупки.
- **основные правила:** `EC-011`, `EC-012`

### 18. `consumer-price-language`

- **тип:** B2C_SERVICE
- **сценарий:** Цена только в иностранной валюте; обязательная информация только не на русском; часть публичной информации foreign-only.
- **основные правила:** `EC-013`, `LANG-001`, `LANG-002`

### 19. `advertising-missing-disclosures`

- **тип:** B2C_SERVICE
- **сценарий:** Блок заранее размечен fixture metadata как подтверждённая интернет-реклама; нет «реклама» и данных рекламодателя.
- **основные правила:** `ADV-001`, `ADV-002`

### 20. `advertising-manual`

- **тип:** B2C_SERVICE
- **сценарий:** Подтверждённый рекламный блок без найденного ERID + маркетинговая подписка с неустановимым механизмом доказательства согласия.
- **основные правила:** `ADV-003`, `ADV-004`

### 21. `auth-uncertain`

- **тип:** SAAS-like fixture classified B2C_SERVICE
- **сценарий:** Российский владелец, auth required; scanner не видит очевидно допустимого способа; требует manual review.
- **основные правила:** `AUTH-001`

### 22. `recommender-missing`

- **тип:** B2C_SERVICE
- **сценарий:** Fixture явно маркируется как использующий рекомендательные технологии; нет notice/rules/contact details.
- **основные правила:** `REC-001`, `REC-002`, `REC-004`

### 23. `recommender-rules-bad`

- **тип:** B2C_SERVICE
- **сценарий:** Рекомендательные технологии подтверждены; rules document закрыт/только на иностранном языке.
- **основные правила:** `REC-003`

### 24. `b2c-company-info-missing`

- **тип:** B2C_SERVICE
- **сценарий:** Юрлицо оказывает услуги потребителям; базовые сведения на сайте не найдены.
- **основные правила:** `CON-001`

### 25. `b2c-ip-info-missing`

- **тип:** B2C_SERVICE
- **сценарий:** ИП оказывает услуги потребителям; сведения о госрегистрации на сайте не найдены.
- **основные правила:** `CON-002`


## Размер набора

- Fixtures: 25
- Rules в Golden Dataset: 50
- Golden cases: 150 (`trigger`, `clear`, `not_applicable`)

Это сознательно меньше, чем «по отдельной странице на каждое правило»: fixtures переиспользуются и покрывают группы родственных rules.

## Следующая материализация

Когда Codex закончит технический scaffold:

1. создать HTML/Next test fixtures по этому плану;
2. scanner должен извлечь из них ожидаемые Facts;
3. Rule Engine прогоняется по `GOLDEN_DATASET_V0_1.yaml`;
4. любые расхождения фиксируются как scanner defect, rule defect или fixture defect;
5. только после стабильного regression rules включаются в MVP.
